# CUA-Lark Advanced Product Plan

版本：`v4.0`

日期：`2026-04-28`

目标截止：`2026-05-07`

状态：`OPC 模式进阶版方案`

## 1. 核心重定义

这次产品不能再只围绕：

1. `帮我约`
2. `帮我发`
3. `帮我记`

这三个动作只够构成一个轻量助手，不够构成一个能让评委记住、也不够支撑三个人并行开发的产品。

所以这次直接升级主定位：

**CUA-Lark = 面向 OPC（One-Person Company / 超级个体）的 AI 协作操作中枢。**

用户不是把它当成一个“会点飞书”的小工具，而是把它当成：

1. 自己在飞书里的 AI 工作台
2. 多个 AI 任务流的并行调度入口
3. 飞书内外任务回流与追踪中心
4. 能前台代操作、也能后台静默执行的混合 Agent 系统

一句话定义：

**用户开启 OPC 模式后，CUA-Lark 会像一个灵动岛式的 AI 中枢，帮他并行管理飞书内协作任务、外部 AI 工具接入、注册表单填写、内容生产和结果回流。**

## 2. 为什么 OPC 模式才是更强的比赛答案

## 2.1 用户价值更大

会议只是 OPC 用户工作中的一个子动作。

真正高频、更痛的，是下面这些混合任务：

1. 注册和管理多个 AI 工具
2. 收集 waitlist、邀请码、表单、申请链接
3. 在飞书里管理项目、素材、文档、提醒和输出
4. 把多个 AI 产出的结果回流到一个可追踪的协作空间
5. 一边在飞书里协调，一边在外部工具里推进执行

也就是说，用户真正要的不是“帮我开个会”，而是：

**帮我把一个人公司的运营链路跑起来。**

## 2.2 比赛要求也允许这种升级

比赛要求是：

1. 基于视觉多模态理解
2. 像真实用户一样操作飞书桌面端
3. 完成跨产品流程
4. 给出验证和评测结果

这并不限制我们只能做飞书内部单一任务。

反而更强的做法是：

1. 把飞书作为主协作中枢
2. 把外部 AI 工具和网页表单纳入任务编排
3. 让视觉桌面 CUA 在飞书主链里承担核心决策和执行
4. 对外部站点优先采用后台无鼠标执行方式

这样既保留比赛题意，又比“只做飞书内部几个动作”更完整。

## 2.3 更符合三个人 + AI 辅助开发的工作量结构

如果做 OPC 模式，三个人的工作天然能拉开成三条线：

1. 飞书桌面执行主链
2. 灵动岛 / 控制台 / 任务中心产品壳
3. 多 Agent 编排 / 后台执行 / 任务回流与验证

这就不再是一个人能很快做完的 Demo，而是一个有明确系统边界的进阶产品。

## 3. 用户画像重构

## 3.1 第一优先用户：OPC 超级个体

这里的 OPC 指：

1. 独立开发者
2. AI PM / AI 创业者
3. 内容创业者
4. 小团队负责人
5. 黑客松队长 / 独立项目 owner

他们的共性是：

1. 自己一个人同时盯产品、运营、内容、协作、申请、增长
2. 同时使用飞书和多个外部 AI 工具
3. 高度依赖表单、注册、申请、信息收集、内容整理、项目同步
4. 没有精力在多个软件之间重复搬运信息

## 3.2 用户真实任务不是“按钮任务”，而是“并行运营任务”

对这类用户来说，真实高频任务是：

1. 找到新的 AI 工具并完成注册 / waitlist / 申请
2. 把工具信息、申请状态、评测结果同步到飞书
3. 在飞书里协调项目、安排会议、分发任务、沉淀文档
4. 让多个 AI 代理同时跑研究、内容、开发辅助等任务
5. 查看哪个任务卡住了、哪个 AI 产出了结果、哪些需要人工确认

所以产品的核心不是“任务执行器”，而是：

**AI 运营中枢**

## 4. 进阶版产品定位

## 4.1 产品名

**CUA-Lark OPC Mode**

## 4.2 一句话价值

**让一个人也能在飞书里并行管理多个 AI、多个工具、多个任务流。**

## 4.3 产品本质

它不是一个单一 Agent，而是一个包含三种执行方式的混合系统：

1. `Feishu Desktop Agent`
2. `Background Web Agent`
3. `AI Task Router & Validator`

其中：

1. 飞书桌面端场景由视觉 CUA 主链负责
2. 外部网站、注册表单、工具接入优先走后台浏览器 / 非抢鼠标执行
3. 结果统一回流到飞书和控制台

## 5. OPC 模式产品形态

## 5.1 OPC Mode 开关

进入产品后，不是直接做单个任务，而是先提供一个：

`开启 OPC 模式`

开启后系统进入“持续运行”的工作台状态，而不是一次性命令状态。

OPC 模式下的体验应该包括：

1. 灵动岛出现
2. 任务队列启动
3. 多 Agent 并行运行
4. 飞书成为任务回流与协作主界面

## 5.2 Status Island / 灵动岛

灵动岛不是装饰，而是 OPC 模式的核心入口。

它负责展示：

1. 当前活跃任务数
2. 正在运行的 Agent 数
3. 当前被卡住的任务
4. 需要人工确认的动作
5. 点击后跳回控制台

这部分可以借鉴 `open-vibe-island` 的形态，但内容完全围绕任务运营，而不是代码 Agent。

## 5.3 Mission Console / 任务控制台

这是整个产品的主页面。

它不是只放一个输入框，而是要像“个人公司总控台”。

至少包括：

1. `Quick Prompt`
2. `任务卡入口`
3. `任务队列`
4. `Agent 状态栏`
5. `飞书回流面板`
6. `外部工具接入区`

## 5.4 Result Hub / 结果回流中心

所有 Agent 的产出都要回到这里。

包括：

1. 已完成注册
2. 已提交表单
3. 已创建的飞书会议 / 文档 / 消息
4. 失败任务和失败原因
5. 推荐下一步动作

## 6. 任务流重构：从会议场景升级为 OPC 运营场景

## 6.1 主场景：AI 工具接入与运营中枢

这是应该成为主线的核心故事：

`我是一个 OPC 用户，我需要持续发现、接入、试用、记录和管理多个 AI 工具，同时在飞书中管理项目、文档、沟通和后续行动。`

## 6.2 八条核心任务流

### 任务流 1：AI 工具注册与表单填写

用户输入：

`帮我把这几个 AI 工具的官网打开，填写注册表单和 waitlist 申请，并把结果记录到飞书。`

系统执行：

1. 打开或后台启动浏览器任务
2. 逐个进入工具官网
3. 填写注册 / 申请表单
4. 获取提交结果
5. 回写飞书文档或任务记录

这是 OPC 模式最核心、最差异化的任务流之一。

### 任务流 2：AI 工具信息归档

用户输入：

`帮我把今天看的 5 个 AI 工具整理成飞书文档，包含名称、用途、注册链接和备注。`

系统执行：

1. 从浏览器任务结果里抽取信息
2. 打开 `Docs`
3. 新建工具收集文档
4. 结构化写入信息

### 任务流 3：飞书项目协同初始化

用户输入：

`帮我为这个新项目在飞书里完成协作初始化。`

系统执行：

1. 创建项目说明文档
2. 创建启动会议
3. 发送群内通知
4. 在结果页汇总初始化完成状态

### 任务流 4：会前准备

用户输入：

`帮我完成这次项目会前准备。`

系统执行：

1. 建会
2. 补文档
3. 发通知

会议场景保留，但变成 OPC 主线里的一个子任务流。

### 任务流 5：多 AI 并行研究

用户输入：

`让三个 AI 分别研究这个方向、给出竞品总结、生成功能建议，并把结果回到飞书。`

系统执行：

1. 启动多个 AI 任务 worker
2. 并行请求不同 AI / runner
3. 汇总结果
4. 回写飞书文档或结果页

### 任务流 6：内容生产与发布准备

用户输入：

`帮我生成一版产品介绍、整理进飞书文档，并列出待发布事项。`

系统执行：

1. AI 生成内容草稿
2. `Docs` 沉淀文档
3. 在控制台生成待办清单

### 任务流 7：提醒与跟进

用户输入：

`帮我提醒今天没回复的合作方，并把已提醒的对象记录下来。`

系统执行：

1. 打开 `IM`
2. 搜索会话或使用当前会话
3. 发送跟进消息
4. 回写结果

### 任务流 8：一键运营冲刺

用户输入：

`帮我完成今天的 OPC 冲刺：注册 3 个工具、整理 1 份文档、同步 1 次飞书消息。`

系统执行：

1. 任务拆解
2. 多 Agent 编排
3. 前后台混合执行
4. 最终结果回流

这条是答辩最强的旗舰场景。

## 7. 三类执行方式

## 7.1 前台视觉执行

适用：

1. 飞书桌面端真实交互
2. 比赛要求的核心主链
3. 需要展示“像真实用户一样操作”的场景

典型动作：

1. 打开 `IM`
2. 打开 `Calendar`
3. 打开 `Docs`
4. 点击、输入、发送、保存

## 7.2 后台无鼠标执行

适用：

1. 外部网站
2. 注册表单
3. waitlist 申请
4. 工具信息抓取
5. 可在浏览器沙箱中进行的动作

执行方式：

1. Headless Chromium
2. Browser agent
3. DOM / 语义辅助定位
4. 不抢占本机鼠标

这条线对 OPC 模式很关键，因为用户不可能接受所有外部任务都抢前台。

## 7.3 后台纯任务执行

适用：

1. AI 生成摘要
2. 内容写作
3. 信息整理
4. 任务分类与汇总
5. 报告生成

执行方式：

1. 多 AI worker
2. Queue
3. Background job

## 8. 多 Agent 协同模型

## 8.1 四个角色 Agent

为了让产品不像“一个大而全的黑盒”，建议拆成四类 Agent 角色：

### Agent A：Scout

负责：

1. 发现工具
2. 打开链接
3. 收集官网和表单入口

### Agent B：Operator

负责：

1. 表单填写
2. 注册提交流程
3. 飞书桌面操作

### Agent C：Writer

负责：

1. 文档生成
2. 摘要整理
3. 汇总输出

### Agent D：Coordinator

负责：

1. 任务编排
2. 优先级排序
3. 结果回流
4. 人工确认触发

## 8.2 控制台中的多 Agent 可视化

控制台里不该只显示一个“运行中”。

应该能看到：

1. 哪些 Agent 在运行
2. 每个 Agent 在做什么
3. 哪个 Agent 卡住了
4. 哪些结果已经回流

## 14. 最终判断

**OPC 用户的飞书 AI 运营中枢。**

这才是更值得三个人并行去做、也更有机会在比赛里形成明显差异化的路线。
