# CUA-Lark PRD

版本：`v3.0`

日期：`2026-04-28`

状态：`基于最新会议纪要重写 / OPC Mode 比赛版 PRD`

## 1. 产品结论

`CUA-Lark` 本次比赛的最佳产品定位，不再是：

1. 泛功能桌面 Agent
2. 只围绕会议的轻助手
3. 飞书外部应用的大而全自动化平台

而是：

**一个面向 OPC（One-Person Company / 超级个体）的飞书内部协作 AI 中枢。**

这次产品要解决的问题不是“帮用户点一次按钮”，而是：

**让 OPC 用户在飞书内部，用一个 AI 中枢并行管理会议、文档、IM、任务同步和多 Agent 内容生产。**

一句话定义：

**CUA-Lark OPC Mode = 用户开启 OPC 模式后，一个带灵动岛状态入口的飞书 AI 工作台，帮他在飞书内部并行推进多子产品协作任务。**

## 2. 基于本次会议的关键方向调整

## 2.1 用户群体聚焦：OPC 超级个体

本次会议后的共识非常明确：

1. 产品不再面向“泛用户”。
2. 产品优先服务 `OPC` 用户。
3. 这类用户的核心工作特征是：
   - 同时做产品、运营、内容、沟通和管理
   - 强依赖 AI 工具协作
   - 需要多线程任务并行推进
   - 需要一个统一的协作与进程管理中枢

因此，产品必须从“功能集合”转向“工作流中枢”。

## 2.2 场景收敛：只做飞书内部子产品联动

本期比赛版明确约束：

1. 只做飞书内部子产品联动
2. 不扩展到美团、外卖、外部业务系统等跨应用场景
3. 允许围绕 OPC 用户做任务设计，但任务必须主要落在飞书生态内

也就是说，本期核心产品域限定为：

1. `IM`
2. `会议 / 日历`
3. `云文档`
4. `多维表格`
5. `视频会议 VC`
6. `邮箱 Mail`

这样做有三个好处：

1. 更符合比赛题目对飞书桌面 / 飞书生态的聚焦要求
2. 更容易在 `5月5日` 前做出稳定闭环
3. 更容易形成“跨子产品联动”的加分点

## 2.3 技术路径调整：优先飞书浏览器版 + 浏览器沙箱

本次会议明确的技术策略是：

1. **优先基于飞书浏览器版开发**
2. **优先使用浏览器沙箱执行**
3. 避免桌面版前台抢鼠标问题影响开发与演示

因此比赛版的执行策略改为：

1. 浏览器版飞书为主执行环境
2. 视觉理解和页面交互仍然保留 Agent 特征
3. 跨子产品联动可借助飞书 CLI、机器人或内部能力做辅助
4. 桌面端真实鼠标控制保留为补充能力或后续增强

## 2.4 MVP 节点前移：5月5日前必须合并核心工作流

这次会议把时间线收得更紧：

1. `5月5日` 是功能合并底线
2. 在此之前必须至少完成 `1` 条核心工作流
3. 至少覆盖 `2` 个飞书子产品联动

推荐目标工作流是：

`会前准备`

也就是：

1. 建会
2. 生成会议文档
3. 发通知

这条工作流同时覆盖：

1. `会议 / 日历`
2. `云文档`
3. `IM`

并且非常适合答辩演示。

## 2.5 风险应对：权限不通时保留灵动岛独立产品 fallback

会议里已经形成的风险兜底策略是：

1. 如果飞书权限、CLI、机器人或关键链路受阻
2. 则把 `灵动岛 + 进程管理可视化` 先做成独立可展示产品
3. 用它承载任务状态、Agent 运行态、结果回流展示

所以本期产品其实有两层交付：

1. 正常路径：飞书内部子产品联动产品
2. 风险路径：灵动岛式 AI 进程管理产品

## 3. 为什么这条路线合理

## 3.1 比赛要求允许我们做“飞书内部工作流产品”

赛题的本质要求是：

1. 借助视觉多模态理解
2. 像真实用户一样操作飞书环境
3. 做跨产品流程
4. 输出状态验证和评测报告

这并不要求我们把范围做得很广，反而鼓励我们：

1. 在飞书生态内收敛
2. 把一个真实工作流打透
3. 把进程可视化、验证和评测做扎实

## 3.2 OPC 用户与飞书生态天然匹配

飞书本身就是典型的 `All-in-One` 协作基座：

1. `IM`
2. `会议 / 日历`
3. `云文档`
4. `多维表格`

对 OPC 用户来说，这类一体化协作环境非常适合做：

1. 任务集中管理
2. AI 内容回流
3. 项目初始化
4. 会议前后准备
5. 多线程任务同步

因此，用飞书作为 OPC 用户的 AI 中枢，比做跨很多外部应用更合理。

## 3.3 Benchmark 和市场数据仍支持这条路径

当前主流 benchmark 说明：

1. `OSWorld` 中人类与 Agent 之间仍有明显差距，说明 CUA 仍处早期。[OSWorld](https://os-world.github.io/)
2. `ScaleCUA` 和 `GUI-R1` 证明高质量 GUI 数据和闭环反馈可以显著拉升能力。[ScaleCUA](https://openreview.net/forum?id=yBFUqdJFZn) [GUI-R1](https://huggingface.co/papers/2504.10458)
3. `macOSWorld` 证明跨界面、跨语言、多平台任务仍然很难。[macOSWorld](https://papers.cool/arxiv/2506.04135)

市场侧同样支持：

1. 协同软件市场持续增长。[Grand View Research](https://www.grandviewresearch.com/industry-analysis/enterprise-collaboration-market-report)
2. 智能流程自动化市场高速增长。[Grand View Research](https://www.grandviewresearch.com/press-release/global-intelligent-process-automation-market)

所以，“在飞书内部做可解释、可验证的 OPC 工作流 Agent”既符合题目，也符合趋势。

## 6. 产品核心创新点

## 6.1 创新点 1：从单次自动化升级为 OPC 工作流中枢

产品不只做单任务，而是做：

1. 工作流发起
2. 多步骤联动
3. 多线程任务进度管理
4. 结果回流

## 6.2 创新点 2：聚焦飞书内部多子产品联动

本期最大的产品亮点不是范围广，而是联动深：

1. `会议 / 日历`
2. `云文档`
3. `IM`
4. `多维表格`
5. `视频会议 VC`
6. `邮箱 Mail`

围绕这些产品做跨域联动，更符合比赛加分逻辑。

## 6.3 创新点 3：引入灵动岛式进程管理可视化

灵动岛不是装饰，而是：

1. 当前任务状态入口
2. 当前进程和 Agent 状态展示
3. 当前阻塞与确认节点入口
4. 整个 OPC 模式的轻量常驻界面

## 6.4 创新点 4：浏览器沙箱优先，降低演示风险

浏览器版飞书的方案价值在于：

1. 不抢鼠标
2. 更容易稳定录屏与演示
3. 更适合多子产品联动调试
4. 更适合作为当前阶段的 MVP 主实现路径

## 8. 核心场景

用户输入：

`帮我把这次推进结果沉淀并继续跟进`

系统完成：

1. 信息写入文档或多维表格
2. 通过 Mail 或 IM 继续跟进
3. 必要时关联 VC 或后续会议

## 9.3 3.3 进阶能力（加分项）

本期除了 `3.2` 的核心功能实现，还必须围绕比赛截图中的 `3.3 进阶能力` 做加分设计与分工落地。

但这里有一个执行前提必须写清楚：

**以下 `3.3` 进阶能力，不抢占 `5月5日` 前核心主链的开发资源。只有在各自子产品主链和基础联动链跑通、并且团队还有余力的情况下，才继续向下做深。**

也就是说，优先级顺序始终是：

1. 子产品基础 demo
2. 子产品多步链
3. 联动链
4. 最终整合 demo
5. `3.3` 进阶能力加分项深化

### 进阶能力 1：异常场景处理

目标：

1. 自动识别并应对弹窗干扰
2. 自动识别权限不足提示
3. 自动识别加载超时与页面失焦

面向 OPC 用户的延伸深度：

1. 当用户同时推进多个任务时，系统要能识别“当前是哪条任务被弹窗或权限问题阻塞”
2. 在灵动岛或运行态里明确展示“阻塞的是哪条工作流”，而不是只报通用错误
3. 当一个任务失败时，不影响其他并行任务继续推进

### 进阶能力 2：跨产品联动测试

目标：

1. 验证 `IM -> Calendar`
2. 验证 `Calendar -> Docs`
3. 验证 `Docs -> VC`
4. 验证 `Docs / Base -> Mail`

面向 OPC 用户的延伸深度：

1. 不是只验证一次跳转，而是验证“一个人公司”的完整推进链
2. 例如从 `IM` 接收任务 -> `Calendar` 安排会议 -> `Docs` 沉淀方案 -> `Mail` 对外触达
3. 让飞书内部子产品真正承担“个人运营中枢”的角色

### 进阶能力 3：自愈式执行

目标：

1. 操作失败后自动分析原因
2. 尝试替代路径完成任务
3. 保留失败节点和恢复记录

面向 OPC 用户的延伸深度：

1. 当某条链路失败时，不是简单重试，而是尝试“换一种推进方式”
2. 例如会议创建失败时，先生成文档和通知草稿，避免整条任务彻底中断
3. 对 OPC 用户来说，关键不是某一步完美，而是整体推进不断档

### 进阶能力 4：测试用例自动生成

目标：

1. 基于飞书功能文档或录屏
2. 自动生成结构化测试用例草稿
3. 支持后续人工修订

面向 OPC 用户的延伸深度：

1. 不只生成“测试 case”，还可以沉淀“工作流模板”
2. 例如自动抽出“会前准备模板”“文档同步模板”“会后沉淀模板”
3. 让超级个体后续重复任务不需要重新从零配置

### 进阶能力 5：混合定位策略

目标：

1. 视觉识别主决策
2. 结合 `Accessibility Tree / DOM`
3. 提升元素定位精度和稳定性

面向 OPC 用户的延伸深度：

1. 在高频协作链路中优先保障关键动作稳定性
2. 比如发消息、建会、写文档、写邮件这类“高价值节点”
3. 让系统在复杂页面和高并发任务下仍能保持可控

### 进阶能力 6：多轮对话编排

目标：

1. 根据中间执行结果
2. 动态调整后续测试步骤
3. 支持多步任务迭代推进

面向 OPC 用户的延伸深度：

1. 支持用户像在带助理一样连续下发任务
2. 例如先说“帮我准备周五的产品会”，再补一句“再顺便把纪要模板建好”
3. 系统需要把后续意图接进已有工作流，而不是每次重开新任务

### 进阶能力 7：录制回放

目标：

1. 录制人工或 Agent 操作轨迹
2. 生成可复用的自动化脚本或回放序列

面向 OPC 用户的延伸深度：

1. 把个人高频工作流沉淀成可复用“个人 SOP”
2. 例如周会准备、周报同步、项目通知、内容归档
3. 让系统逐步从“帮一次”变成“持续替你跑”

## 10.2 三层执行架构
