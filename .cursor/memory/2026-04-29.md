## [23:37] M9 verify-run #2 root cause: BridgeEnvelope wire schema 字段名跟 TS BridgeCodec 假设不一致

**Type**: correction
**Tags**: `bug`, `m9`, `protocol`
**Related**: commit `9f683bb`；[[2026-04-29#23:31]]

加 verbose log 后 verify-run #2 直接告诉答案：

```
bridge event: type=webAgentTaskCompleted taskID=<no-taskID>
bridge event webAgentTaskCompleted skipped: taskID=<missing> != inFlight.taskID=feishu-bot-...
```

事件正常 fan out 来了，但 `payload.taskID` 抽出来空。

根因：Swift `BridgeServer` 编码 `AgentEvent` 时 payload 嵌套在**跟 type 同名的 key** 下：`{type: "webAgentTaskCompleted", webAgentTaskCompleted: {taskID: ...}}`，**不是**  `{type: ..., payload: {...}}`。`runners/web-agent/src/bridge/codec.ts` 的 `decodeAgentEvent` 在 decode 时把 `event[type]` 重命名为 `payload` 暴露给 observer-client.ts。bot bridge 直接 raw JSON.parse 没经过 codec，`payload` 是 undefined。

修：在 `main.ts` socket data handler 中收到 event envelope 时立即 normalize：

```ts
const wireType = evRaw.type;
if (typeof wireType === 'string' && evRaw[wireType] && !('payload' in evRaw)) {
  evRaw.payload = evRaw[wireType];
}
```

跟 codec.decodeAgentEvent 等价，后续 `handleBridgeEvent` 整套不用改。

**教训**：跨语言 IPC 的 schema 假设错位是经典坑；m10 应该写一个 in-memory BridgeServer fake 让这种 schema drift 在 CI 抓到，避免端到端 5 分钟才能复现。

**Status**: ✅ verified（verify-run #3 看到完整 `Started → StepUpdate → Completed → sending reply` 链路 + 飞书 IM 收到回执）

## [23:41] M9 verify-run #3 微 bug: 同一 prompt 重发时 ack-reply 被飞书幂等去重

**Type**: correction
**Tags**: `bug`, `m9`, `idempotency`
**Related**: commit `622ac1e`

verify-run #3 用户对同一 prompt "hello bot, what is 1+1" 连发两次。第一次：ack "已收到" + 完成 ✅。第二次：**只**有完成回执，**没有** "已收到"。

根因：`reply.ts` 用 `md5(chatID + text)` 当 idempotency-key。第二次发完全相同 prompt 时 ack-reply 文案"已收到：hello bot, what is 1+1\n正在执行…"完全相同 → key 命中飞书 server 的幂等检查 → 直接返回成功**不真发**。同款机制会让 busy/completed/failed reply 在重发场景下也隐身。

修：`ReplyArgs.nonce` 可选字段拼进 hash。每个调用点带唯一上下文：
- ack/busy 用 `ack-${msg.messageID}` / `busy-${msg.messageID}`
- approval/completed/failed 用 `approval-${taskID}` / `completed-${taskID}` / `failed-${taskID}`

每条飞书 messageID 唯一 → 同 prompt 重发 nonce 不同 → 真发；同任务重试 nonce 相同 → 幂等正确去重。

**Status**: ✅ verified（重发同 prompt 收完整 ack + 终态回执）

## Pattern: M5/M6/M7/M8/M9 OpenSpec change 工作流稳定下来

**Type**: optimization
**Tags**: `process`, `architecture`, `openspec`

每个 milestone 走 OpenSpec change 流程的拆 commit 模板（M7→M8→M9 三轮一致，无需再发明）：

1. `docs(openspec): propose <name>` — proposal/design/tasks/specs delta，validate --strict 通过
2. 若干 `feat(...)` / `fix(...)` 实施 commit，每个聚焦一组 task
3. `docs(openspec): <name> task tracking + post-implementation retrospective` — 把实测数字（step 数 / 用时 / 是否触发 login_qr / 屏幕实拍是否通过）写到 tasks.md `## N. Post-implementation retrospective` 段
4. `chore(openspec): archive <name>` — 用 `npx @fission-ai/openspec archive <name> --yes` 移动目录 + sync deltas 进 `openspec/specs/`

每个 hotfix（archive 后实测发现的 bug）走单 commit `fix(...)` 直接修，不再开新 change（保留 archive 节奏）；hotfix retrospective 写在原 archive `tasks.md` 的 `§N retrospective` 末尾追加（M6 §9 / M7 §6 / M8 §7 都是这种 retrospective 形态）。

**spec sync gotcha**：`### Requirement: <header>` 必须**完全字面**匹配现有 spec 的 header 才能 MODIFY；改 header 文字会让 archive 命令报 `header not found`。即使语义已变（"三个内置 skill" → "五个内置 skill"），保留原 header 文字 + 在 body 描述变化是最稳的做法（M8 spec sync 踩过坑）。
