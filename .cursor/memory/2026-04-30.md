| Calendar create event | 46 | 209.3s | 9 (5/10/15/20/25/30/35/40/45) | completed ✅，事件 5月1日 15-16 真落地 |

heartbeat 节奏稳定 19-25 秒一条，IM 端"沉默感"完全消除。

### 关键决策

- **tenant URL 是飞书日历的真解** —— `calendar.feishu.cn` 没 A 记录、`www.feishu.cn/messenger/` redirect 后 sidebar 找不到 calendar 图标，唯一可达的是 `<tenant>.feishu.cn/calendar/week`。这个发现来自用户提供的真实可访问 URL。
- **calendar 步数预算 25 → 实测 46**，超 2x 但 ran-to-completed。视为 m10 范围内的可接受代价（m9 是 call_user 退出，从"完全 block"到"步数多但成功"是质的飞跃）。step 压缩留 m11+。
- **heartbeat 设计的双门控正确**：单 step 门控会被 5/5s 快任务穿透，单时间门控会漏长间隔单步任务。组合两个门控后 calendar 任务的 9 条 heartbeat 实测节奏完美贴合用户体感。
- **idempotency-key nonce 必须含 stepIndex**：m9 §9.2 教训重学一遍——同 chat / 同 reply 文案模式如果 nonce 不变会被飞书 server dedupe 静默吞掉。

### Gotcha

- **chromium SingletonLock 残留**：上次 dev.sh 没 graceful shutdown 时 `~/Library/Application Support/LarkIsland/web-agent/profiles/{generic,feishu}/SingletonLock` 会留下，新 runner 启动时 chromium 拒绝复用 profile。dev.sh 启动前清这两个文件可避免。可以加到 dev.sh 自动清理（m11 backlog）。
- **lark-cli event +subscribe 单实例锁**：用户上次手动起的 lark-cli subscribe 没退出 → 新 dev.sh 起 bot bridge 时 lark-cli 报 "another event +subscribe instance is already running"。dev.sh 可以加 `--force`（m11 backlog），现在暂用手动 kill。
- **vitest 顶层 import 副作用**：feishu-bot/src/main.ts 直接 `main()` 导致 heartbeat.test.ts import helper 时整个 main 跑起来 spawn lark-cli + connect socket + process.exit(1)。修法：`isEntry` 判断（比较 `import.meta.url` 与 `process.argv[1]`）。这个模式以后所有有 side effect 的 main module 都该用。

## 13:00–13:35 m11 archive — bot workflow orchestration ✅

### 范围

5/2 demo 价值倍增 milestone：bot bridge 收到飞书 IM 复合指令时自动拆解为多 step 任务串。

实现：
1. `splitWorkflow(text)`：cheap regex keyword gate。命中 `[，,；;] (并|然后|接着|再|另外)` / `并通知` / `顺便` 才继续。
2. `callPlanLLM(text)`：OpenAI-compatible `/chat/completions` 调 qwen-plus，response_format=json_object 强制 JSON 输出 `{steps: [{description, prompt}]}`，2-3 步上限。
3. `renderTemplate(prompt, ctx)`：`$prev_result` 占位符延后绑定，step i>0 拿到 step i-1 的 finalAnswer 全文。
4. WorkflowExecutor in main.ts：sequence dispatch + 跨 step 共享 heartbeat 计数器（D6）+ 5 段 IM lifecycle reply（🔀/▶️/✅/❌/wf-fallback）。
5. fail-safe：keyword miss / planLLM not configured / LLM HTTP 错 / JSON 错都退化到 m9 single task 路径。

### 实测结果

calendar+IM 联动（"创建一个日程 m11 workflow demo 明天下午4点；并给自己发个消息说日程已建"）：

```
workflow keyword hit; plan-llm ok 2 step(s) planned   ← 2.7s LLM
step0 calendar  22 step / 103.9s   ← 2x 快于 m10 单 task 46 step
step1 IM         6 step /  29.3s
heartbeat: 5/10/16/21（step0 内）/ 26（step1 内 — 跨 step 计数器共享 D6 实测验证）
total: 133s / 28 step / 5 heartbeats / wf-done reply
```

跨 step 计数器共享是 m11 的关键设计（D6）—— 每 step 重置就永远不会触发 heartbeat。实测在 step1 IM 任务才 6 step 但因为跨 step totalSteps=26 触发了一条 heartbeat。

### 关键发现

- **LLM plan 简化 prompt 反向加速 runner**：m10 单 task 跑 calendar 是 46 step（要在一个 prompt 里管"创建+发消息"），m11 拆成原子 step prompt 后单纯 calendar 22 step / 2x 加速。这不是 m11 设计预期的，是个意外正向反馈。
- **fail-safe 多重跌落**：实测中实际命中 3 次跌落路径——dev.sh 没透传 env / regex 没匹配分号 / lark-cli lock 不释放——bot 都没崩，全部退到 m9 single task 路径继续工作。
- **plan LLM cost ~0.001 USD/次**：可以放心用。

### Gotcha（4 个 hotfix）

1. **regex 漏分号**：原 `[，,]` 只匹配逗号，用户实际 prompt 用 `；`。修：`[，,；;]`。
2. **dev.sh 没透传 DASHSCOPE_API_KEY**：bot bridge 不像 runner 用 dotenv-runtime，只能靠 dev.sh source `web-agent/.env` 然后透传到子进程。修：`set -a / source .env / set +a` + 显式 K=V override。
3. **`??` 不跨空字符串 fallback**：dev.sh inline `K="${K:-}"` 透传空字符串 ≠ undefined，nullish coalescing 不回退。修：`nonEmpty(v)` helper coerce '' 到 undefined。
4. **lark-cli `event +subscribe` 单实例锁 30s 才释放**：dev.sh 频繁重启会撞锁导致 bot 自杀。修：bot 启 lark-cli 加 `--force` 跳过 server-side 锁检查（dev.sh-level pkill 还在保单实例语义）。
